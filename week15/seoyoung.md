## 문제 1

### 문제 정보

* 문제명: 가장 먼 노드
* 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/49189
* 사용한 알고리즘 / 자료구조: BFS(너비 우선 탐색), 인접 리스트

### 처음 접근 방식

"가장 먼"이라는 말을 보고 다익스트라를 꺼내야 하는 줄 알고 우선순위 큐부터 만들었다. 거리 배열을 무한으로 채우고 힙에서 꺼낸 노드마다 이웃 거리를 갱신하는 식으로 짰는데, 다 돌려놓고 보니 간선에 가중치가 아예 없었다. 모든 간선이 1이면 힙을 쓸 이유가 없는데 괜히 `log` 하나를 얹은 셈이었다. 그리고 간선 정보를 2차원 인접 행렬로 받아뒀던 게 더 큰 문제였다. 노드가 20,000개까지 들어올 수 있어서 행렬을 만드는 순간 4억 칸이 필요해 메모리부터 터졌다.

### 풀이 방법

1. 간선 목록을 받아 노드 번호별 이웃을 담는 인접 리스트로 바꾼다. 양방향 간선이므로 `a`의 이웃에 `b`를, `b`의 이웃에 `a`를 모두 넣는다.
2. 거리 배열 `dist`를 노드 수 + 1 길이로 만들고 전부 -1로 채워 "아직 방문 안 함"을 표시한다.
3. 1번 노드를 큐에 넣고 `dist[1] = 0`으로 둔다.
4. 큐에서 노드를 꺼내 이웃을 보고, `dist`가 -1인 이웃만 `dist[현재] + 1`로 적고 큐에 넣는다.
5. 큐가 빌 때까지 반복하면 `dist`에 1번에서 각 노드까지의 최단 거리가 채워진다.
6. `dist[2:]` 중 최댓값을 구하고, 그 값과 같은 노드의 개수를 세어 반환한다.

### 어려웠던 지점

방문 체크를 큐에 넣을 때가 아니라 꺼낼 때 하도록 짜놨던 게 오래 걸린 지점이다. 예제는 통과했는데 제출하니 시간초과가 났다. 같은 노드가 이웃 여러 곳에서 중복으로 큐에 들어가서, 간선이 많은 그래프에서는 큐 길이가 폭발했다. 또 `dist`를 0으로 초기화해뒀더니 "거리가 0"인 노드와 "안 가본" 노드가 구분되지 않아 1번 노드로 되돌아오는 경로가 생겼다. 마지막에는 1번 노드 자신까지 후보에 넣어버려서, 간선이 하나도 없는 입력에서 답이 1로 나오는 실수도 했다.

### 해결 방법

방문 표시를 "큐에 넣는 순간"으로 옮겼다. BFS는 처음 도달했을 때가 곧 최단 거리이므로 나중에 다시 만나도 갱신할 일이 없고, 넣을 때 바로 표시해두면 한 노드가 큐에 두 번 들어가지 않는다. 미방문 표시는 -1로 고정해서 거리 0과 섞이지 않게 했다. 최댓값을 구할 때는 시작 노드인 1번을 아예 범위에서 빼고 2번부터만 봤다. 가중치가 전부 1인 걸 확인한 뒤 힙을 걷어내고 `deque`로 바꾸니 코드도 짧아지고 통과했다.

### 시간복잡도 / 공간복잡도

* 시간복잡도: O(V + E)
* 공간복잡도: O(V + E)

`V`는 노드 수(최대 20,000), `E`는 간선 수다. 각 노드는 큐에 한 번만 들어가고 각 간선은 양쪽에서 한 번씩 확인되므로 전체가 선형이다. 인접 리스트가 간선 수에 비례하는 공간을, 거리 배열과 큐가 노드 수에 비례하는 공간을 쓴다.

### 새롭게 알게 된 점

가중치가 모두 같으면 다익스트라가 아니라 BFS가 맞는 도구라는 걸 몸으로 익혔다. 힙으로도 답은 나오지만 불필요한 비용이 붙고, 반대로 가중치가 다른데 BFS를 쓰면 아예 틀린다. 문제를 읽을 때 "간선에 비용이 적혀 있는가"를 먼저 확인하는 습관을 들여야겠다. 14주차 입국심사에서 입력 범위 10억을 보고 접근을 틀었던 것처럼, 이번에도 노드 20,000이라는 숫자가 인접 행렬을 쓰지 말라는 신호였다. 그래프를 받을 때 행렬과 리스트 중 무엇을 쓸지는 노드 수와 간선 수를 비교해서 정하면 된다는 것도 정리됐다.

## 문제 2

### 문제 정보

* 문제명: 표 병합
* 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/150366
* 사용한 알고리즘 / 자료구조: 유니온 파인드(분리 집합), 경로 압축

### 처음 접근 방식

병합을 요구하는 대로 그대로 구현하려고 했다. 50 x 50 격자를 2차원 배열로 두고, `MERGE`가 들어오면 두 셀이 속한 그룹의 모든 칸을 돌면서 같은 값으로 덮어쓰는 식이었다. 그룹을 찾으려고 매번 2,500칸을 전부 훑었고, `UNMERGE`에서는 그 그룹에 속한 칸을 다시 찾아 해제해야 했다. 명령이 1,000개까지 들어오니 2,500칸 순회가 계속 쌓여서 간신히 돌아가긴 했지만, 그보다 로직이 꼬여서 어떤 칸이 어느 그룹인지 추적이 안 됐다. 병합된 그룹이 또 다른 그룹과 병합될 때 값이 뒤섞이는 버그를 못 잡았다.

### 풀이 방법

1. 각 셀을 `(r - 1) * 50 + (c - 1)` 꼴의 번호 하나로 바꿔 1차원으로 다룬다.
2. `parent` 배열을 자기 자신으로 초기화하고, 값은 대표 번호에만 저장하는 `value` 배열을 둔다.
3. `find(x)`는 부모를 따라 올라가 대표를 찾고, 올라간 경로의 노드들을 대표에 직접 연결해 다음 조회를 빠르게 한다.
4. `UPDATE r c v`는 `find`로 대표를 찾아 그 대표의 값만 바꾼다. `UPDATE v1 v2`는 값이 `v1`인 대표를 모두 찾아 `v2`로 바꾼다.
5. `MERGE`는 두 셀의 대표를 구해 다르면 하나를 다른 쪽 부모로 붙인다. 값은 비어 있지 않은 쪽을 남기고, 양쪽 모두 값이 있으면 먼저 지정된 셀의 값을 쓴다.
6. `UNMERGE r c`는 해당 대표가 하나로 합쳐 두고 있던 칸들을 전부 떼어낸다. 떼기 전에 그룹의 값을 따로 저장해두고, 각 칸의 부모를 자기 자신으로 되돌린 뒤 지정된 셀에만 저장해둔 값을 넣는다.
7. `PRINT r c`는 대표의 값을 보고 비어 있으면 `EMPTY`를 출력한다.

### 어려웠던 지점

`UNMERGE`가 제일 까다로웠다. 유니온 파인드는 합치기는 잘하고 떼어내기는 지원하지 않는 자료구조인데, 이 문제는 해제를 요구했다. 트리 모양으로 붙여둔 걸 어떻게 되돌려야 하는지 한참 막혔다. 또 `UPDATE r c v`에서 셀 자리에 값을 바로 쓰다가, 그 셀이 대표가 아닐 때 그룹 전체에 반영되지 않는 버그가 났다. 반대로 `UPDATE v1 v2`에서는 모든 칸을 돌며 값을 바꿨더니 같은 그룹을 여러 번 바꿔 엉뚱한 결과가 나왔다. 경로 압축을 넣은 뒤에는 부모 관계가 납작해져서, 떼어낼 때 "누가 이 그룹에 속했는지"를 트리에서 역추적할 수 없다는 점도 걸림돌이었다.

### 해결 방법

떼어내기는 트리를 역추적하지 말고, 전체 2,500칸을 한 번 훑어 `find`가 그 대표와 같은 칸을 모으는 방식으로 풀었다. 명령이 1,000개이고 칸이 2,500개라 2,500 x 1,000은 충분히 돌아가는 규모였다. 유니온 파인드가 떼어내기를 못 하면 그 부분만 완전 탐색으로 메우면 된다고 받아들이니 막힘이 풀렸다. 값은 반드시 대표에만 저장하기로 규칙을 정해서, 읽고 쓰는 모든 연산을 `find`를 거친 뒤에 하도록 통일했다. 이 규칙 하나로 `UPDATE` 두 종류가 모두 정리됐고, 그룹을 중복으로 건드리는 문제도 사라졌다. 값이 같은 그룹을 바꿀 때도 대표만 모아서 처리하니 한 번씩만 반영됐다.

### 시간복잡도 / 공간복잡도

* 시간복잡도: O(Q * R * C)
* 공간복잡도: O(R * C)

`Q`는 명령 수(최대 1,000), `R * C`는 격자 칸 수(50 x 50 = 2,500)다. `UNMERGE`와 값 기준 `UPDATE`가 매번 전체 칸을 훑으므로 명령당 `O(R * C)`가 들고, `find`는 경로 압축 덕분에 거의 상수로 본다. 공간은 `parent`와 `value` 배열이 칸 수에 비례한다.

### 새롭게 알게 된 점

유니온 파인드의 핵심은 "칸마다 값을 들고 있지 말고 대표 하나에만 들고 있는다"는 설계라는 걸 알게 됐다. 그룹 전체를 수정하는 연산이 대표 한 곳만 고치는 연산으로 줄어들면서, 병합이 몇 번 겹쳐도 값이 뒤섞이지 않았다. 14주차 이중우선순위큐에서 "지울 때 지우지 말고 꺼낼 때 검증한다"로 시점을 옮겼던 것과 비슷하게, 이번에도 "모든 칸에 쓰지 말고 읽을 때 대표를 거친다"로 시점을 옮긴 셈이다. 그리고 자료구조가 지원하지 않는 연산이 하나 끼어 있을 때, 그 연산만 입력 범위를 믿고 완전 탐색으로 처리하는 타협도 유효하다는 걸 배웠다. 격자를 1차원 번호로 눌러서 다루면 인덱스 계산이 훨씬 단순해진다는 것도 챙겼다.

## 문제 3

### 문제 정보

* 문제명: 모두 0으로 만들기
* 문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/76503
* 사용한 알고리즘 / 자료구조: 트리 DFS(후위 순회), 반복문 기반 스택

### 처음 접근 방식

인접한 두 노드를 골라 하나는 1 늘리고 하나는 1 줄이는 연산이라, 어느 쌍을 먼저 고르느냐에 따라 횟수가 달라질 것 같아서 탐색 문제로 봤다. 큰 값부터 처리하면 유리할 것 같아 가중치가 큰 노드를 먼저 이웃에게 떠넘기는 식으로 그리디하게 짰는데, 반례가 바로 나왔다. 어떤 순서로 해도 결국 각 간선을 몇 번 쓰는지만 결정된다는 감은 왔지만, 그 횟수를 세는 방법이 안 떠올라서 한참 헤맸다. 전체 합이 0이 아니면 불가능하다는 것 정도만 먼저 알아챘다.

### 풀이 방법

1. 전체 가중치의 합이 0이 아니면 어떤 연산으로도 맞출 수 없으므로 -1을 반환한다.
2. 간선 목록으로 인접 리스트를 만들고 0번 노드를 뿌리로 정한다.
3. 뿌리에서 시작해 자식을 먼저 처리하는 후위 순회 순서를 만든다.
4. 잎에서부터 올라오면서, 각 노드의 누적값을 부모에게 전부 떠넘긴다.
5. 떠넘기는 양의 절댓값을 답에 더한다. 노드의 누적값이 `x`이면 부모와 잇는 간선을 `|x|`번 쓰는 것이므로 연산 횟수가 그만큼 늘어난다.
6. 부모의 누적값에 자식의 누적값을 더한다. 자식은 이 시점에 0이 되고 다시 볼 필요가 없다.
7. 뿌리까지 올라오면 전체 합이 0이므로 뿌리도 자연히 0이 되고, 누적한 답을 반환한다.

### 어려웠던 지점

"어느 쌍을 먼저 고르는가"에 답이 달려 있다고 착각한 채로 오래 붙잡고 있었다. 순서를 바꿔봐도 횟수가 같다는 걸 작은 예제로 확인하고서야 탐색을 접었다. 구현에서는 재귀로 짰다가 런타임 에러가 났는데, 노드가 300,000개까지 들어와서 재귀 깊이 제한을 넘긴 것이었다. 일자로 늘어선 트리면 깊이가 그대로 30만이 된다. 또 트리라서 부모를 따로 안 들고 있었더니 자식을 보다가 부모로 되돌아가 무한히 왕복하는 버그가 났다. 답이 `int` 범위를 넘을 수 있다는 점도 처음엔 신경 쓰지 않았다.

### 해결 방법

재귀를 걷어내고 스택으로 순회 순서를 먼저 만들었다. 뿌리부터 스택으로 내려가며 방문 순서를 리스트에 쌓아두고, 그 리스트를 뒤에서부터 읽으면 자식이 부모보다 항상 먼저 나오는 후위 순회가 된다. 방문할 때 부모 번호를 함께 기록해서 이웃 중 부모만 건너뛰도록 하니 왕복 문제도 사라졌다. 핵심 발상은 "각 간선을 몇 번 쓰는지는 이미 정해져 있다"는 것이었다. 어떤 서브트리의 가중치 합이 `x`이면, 그 서브트리와 바깥을 잇는 간선은 `|x|`만큼 운반해야 하고 다른 길이 없다. 그래서 순서를 고민할 필요 없이 모든 간선의 운반량을 더하면 답이 된다. 큰 수는 파이썬이 알아서 처리해주지만, 중간 합을 누적할 때 자료형을 의식하는 습관은 들여놓기로 했다.

### 시간복잡도 / 공간복잡도

* 시간복잡도: O(N)
* 공간복잡도: O(N)

`N`은 노드 수(최대 300,000)다. 순회 순서를 만들 때 각 노드를 한 번씩 방문하고, 답을 더할 때 그 순서를 한 번 더 읽으므로 전체가 선형이다. 인접 리스트, 순회 순서 리스트, 부모 배열, 누적값 배열이 각각 노드 수에 비례하는 공간을 쓴다.

### 새롭게 알게 된 점

트리에서 "최소 연산 횟수"를 물으면 연산 순서를 탐색하는 게 아니라, 각 간선이 반드시 처리해야 하는 양을 세는 문제로 바꿀 수 있다는 걸 알게 됐다. 간선을 끊었을 때 생기는 두 덩어리의 합이 운반량을 그대로 정해주므로 선택의 여지가 없고, 그래서 그리디한지 아닌지를 따질 필요조차 없었다. 잎에서 뿌리로 값을 모으는 후위 순회가 이런 "아래에서 위로 정산하는" 계산의 기본 틀이라는 것도 정리됐다. 그리고 노드가 10만 단위면 재귀 대신 스택을 쓰는 걸 기본값으로 두기로 했다. 14주차 보석 쇼핑에서 구간을 전부 만들지 않고 포인터로 깎았던 것처럼, 이번에도 경우를 나열하지 않고 구조에서 바로 답을 읽어내는 쪽이 정답이었다.
